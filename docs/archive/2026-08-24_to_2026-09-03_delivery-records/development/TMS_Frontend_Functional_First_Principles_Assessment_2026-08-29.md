# TMS 前端与功能需求第一性原理评估

- 日期：2026-08-29
- 仓库：`F:\CP-FT数据分析`
- 基线：`f52f646`（`codex/auth-rbac-frontend`）
- 评估方法：业务需求对照、前后端合同审计、自动化测试基线、真实本机页面走查
- 本轮边界：优先功能；不新增 AD/OIDC、HTTPS、证书、密码策略、服务账号 ACL 等安全项目，但不得削弱现有认证、RBAC、Owner、Source Catalog、Manifest 和失败关闭边界

## 1. 结论先行

当前 TMS 已经是一个可运行、可追溯的 CP/FT 接入与治理平台，但一线用户仍会感到它更像“技术控制台”，还不是一套以任务完成为中心的数据分析系统。

问题的核心不是页面不够多，而是以下两条最短业务链尚未完全闭合：

1. **正式数据链**：固定 CP/FT 入口 → 提交 → 自动看到 Job → 补录/重试 → 正式数据 → 分析/明细/导出；
2. **历史分析链**：按业务字段查找 → 选择一组正式数据 → 按 Lot/Wafer/Bin/参数重算 → 图表与明细 → 下钻追溯。

本轮应优先修正数据口径和任务断点，再合并重复入口、减少技术字段、补齐历史分析和 Quick PAT 的关键反馈。奥卡姆剃刀的结论是：**不重写 React 架构、不引入 Redux/微前端/通用图表设计器，不复活旧的手填 ID 页面；围绕现有 React Query、Job 抽屉、Dataset Current、Canonical 查询和 CP/FT 独立图表做最小闭环。**

## 2. 第一性原理：系统为什么存在

TMS 的业务价值可以约化为四个不可再拆的结果：

1. 原始 CP/FT 数据经过已批准 Cleaner 后成为可信的结构化事实；
2. 用户无需理解 Batch、Run、Dataset Version 等内部编号，也能完成一次任务；
3. 任何良率、Bin、参数图表都由当前筛选条件下的数据库事实重新计算；
4. 失败时不产生错误正式数据，并明确告诉用户下一步能做什么。

据此，前端不是 API 的字段展示器，而是对业务任务、异常恢复和决策顺序的编排层。

## 3. 用户任务拆解

| 用户 | 必须回答的问题 | 最短操作链 | 当前主要断点 |
|---|---|---|---|
| CP/FT 一线工程师 | 数据是否处理成功；失败后怎么继续 | 固定入口 → 选择厂家/来源 → 提交 → Job → 补录/重试 → 结果 | 提交后只提示成功，需重新找 Job；动作码不一致导致“重新处理”失效；筛选和 Tab 刷新丢失 |
| 分析/质量工程师 | 历史数据能否按真实条件重新分析 | 业务条件检索 → 多选正式数据 → Lot/Wafer/Bin/参数 → 图表/明细 | 顶层分析页要求手填 Dataset ID；当前查询合同主要是单 Dataset/单值；缺结构化明细入口 |
| 领导/质量负责人 | 良率、未知数据、异常和新鲜度是否可控 | 默认周期 → 核心 KPI → 趋势 → 异常对象 → Job/Dataset 下钻 | 说明和筛选先于 KPI；12 个卡片抢占注意力；趋势仍是表格；英文方法代码暴露 |
| Quick PAT 用户 | 目录会处理哪些文件；结果能否取得 | 选目录 → Manifest 预览 → 运行 → 进度 → 下载 | 执行前看不到递归文件范围；下载异常没有可见反馈；历史记录仅前端分页 |
| 开发/运维 | 本机环境能否可靠复现 | 启动 → 状态 → 测试 → 停止 | PowerShell 7 写出的中文路径状态被 Windows PowerShell 5.1 误读，导致无法正常停止 |

## 4. 已做得好的地方

### 4.1 一线开发工程师视角

- 工程/量产 × CP/FT 四个固定入口明确，未做风险较高的自动类型猜测。
- Cleaner、Worker、Canonical、Dataset Current 和分析已形成可运行主干，厂家差异仍由成熟 Cleaner 承担。
- Job 抽屉已经能展示队列、处理、待补录、失败和成功状态，并保留父子任务追溯。
- 缺 Lot 的日月新/日月光 FT 已具备文件级补录和同 Cleaner Release 恢复链。
- React Query 适合当前服务端状态模型，无需增加新的全局状态框架。
- Source Catalog 和相对路径合同使正式目录处理具备可重复性。

### 4.2 领导视角

- 管理驾驶舱已经统一使用 `PASS / (PASS + FAIL)`，并单独呈现 UNKNOWN，方向正确。
- Dataset Current、质量摘要、Job 和正式分析之间已有下钻基础。
- 生命周期动作区分“非变异导出”和“显式重处理”，降低了用户误解。
- 数据血缘、Cleaner Release、Source、Job 和 Dataset Version 都可追溯，为后续质量管理提供了可信底座。

## 5. 已确认的功能缺陷

### P0：CP 良率口径错误

`backend/app/infrastructure/sql_dataset_service.py` 的 CP Wafer 良率当前按 `PASS / 全部 Unit` 计算，并用“总数 - PASS”作为 FAIL。这会把 UNKNOWN、ABORT 等结果错误计入 FAIL，与管理驾驶舱及冻结口径冲突。

必须统一为：

- `known_count = PASS + FAIL`；
- `yield = PASS / known_count`；
- UNKNOWN/ABORT 单独计数；
- `known_count = 0` 时良率显示“—”，不得伪造为 0%。

### P0：本机状态文件跨 PowerShell 版本不兼容

PowerShell 7 写入无 BOM UTF-8 JSON，而 Windows PowerShell 5.1 读取时未指定 UTF-8。中文工作区路径会乱码，出现“状态属于另一个工作区”，导致正常停止流程失效。

必须建立唯一的 UTF-8 JSON 读函数，并让启动、状态、停止脚本共同使用；不得通过删除状态文件或强杀进程绕过。

### P1：权限语义与分析入口不一致

- 管理查看角色拥有 `DATASET_READ`/`MANAGEMENT_READ`，没有 `ANALYSIS_RUN`；
- 后端 Dataset 图表读取只要求 `DATASET_READ`；
- 前端 `/analytics` 却要求 `ANALYSIS_RUN`，管理页和 Dataset 页会把用户送到 403。

“查看已存在数据的图表”应使用 `DATASET_READ`；`ANALYSIS_RUN` 只用于创建新的 Quick 计算任务。

### P1：Job 可用动作码前后端不一致

后端返回 `REPROCESS_BATCH`，前端只识别 `REPROCESS`，导致真实可用的重新处理按钮被禁用。现有前端测试使用了不存在的模拟动作码，未发现合同漂移。

### P1：导航默认页和父路由不可靠

- `/` 固定落到 `/production/cp`，仅有管理/审计能力的合法角色可能直接看到 403；
- `/engineering`、`/production` 出现在可见路径中，但没有对应页面；
- 菜单定义、权限判断和页面渲染由多套逻辑维护。

应让根路径和父路径重定向到当前用户可访问的第一个叶子页面；显式访问无权限 URL 时仍然 403。

### P1：正式提交后任务链断开

上传成功后只有 Toast 和列表刷新，没有自动打开返回的 Job，也没有突出新批次。用户必须再次搜索刚创建的任务。

### P1：历史二次分析没有达到业务合同

业务基线要求按上传任务、Lot、Wafer、Bin 和多个参数从数据库重算，并查看清洗明细。当前顶层分析页仍暴露 Dataset ID/version，主要支持单 Dataset、单 Lot、单 Wafer、单参数。

这不是简单增加控件即可解决，必须增加有边界的服务端查询合同、分页明细和 Spec 兼容性判断。

### P1：BR-02 多 Lot 相同 Spec 仍被失败关闭

当前 CP writer 为避免错误 Spec 绑定，对任意多 Lot 输入抛出 `CP_MULTI_LOT_SPEC_BINDING_REQUIRED`。这是正确的失败关闭，但 BR-02 要求“同 Spec 多 Lot可入库并可合并/分 Lot 分析”。最小正确实现是先证明所选 Lot 的参数、单位、测试条件和上下限一致，再允许共享 Spec；不同 Spec 继续失败关闭。

### P1：Product 补录未进入当前主流程

旧的 enrichment 组件未挂载；当前 Active UI 只有 Lot 恢复。缺 Product 时，一线用户没有可见的“填写或跳过”入口，Product 修改也没有完整地影响 Current 查询事实。

### P2：信息架构和页面密度过高

- 正式工作台与 Dataset Current 首屏被大量统计卡片、说明和筛选占据，关键表格位于折叠线下；
- 宽表暴露大量技术 ID、SHA、Release 和 Intent；
- “能力中心”是参考说明，不是日常任务；
- 顶层“分析图表”与 Dataset/Job 上下文入口重复；
- `StageIntakeWorkbench`、`DatasetReview`、`JobWorkbench`、`HuaHongInspector` 四套旧组件无生产入口，仍保留手填内部 ID 或旧人工发布语义。

### P2：管理视图的决策顺序反了

筛选和方法说明先于核心指标，12 个 KPI 同权展示，趋势用表格呈现。管理首屏应先回答：当前良率、UNKNOWN 占比、异常、数据新鲜度；其余维度按需展开。

### P2：Quick PAT 缺少执行范围确认与失败恢复

创建任务前没有递归 Manifest 预览，下载失败未转成可见错误，历史会话全量加载后在浏览器分页。

## 6. 奥卡姆剃刀评估

| 决策 | 本轮做法 | 原因 |
|---|---|---|
| 保留 | 四个固定正式入口、React Query、Job 抽屉、Dataset Current、Quick PAT、CP/FT 独立图表 | 已验证且直接服务业务任务 |
| 合并 | 分析入口进入“历史正式数据/任务结果”；能力说明进入厂家选择帮助 | 减少重复入口和无上下文页面 |
| 渐进披露 | SHA、Cleaner Release、Intent、Worker、血缘、方法口径、生命周期说明 | 追溯信息必须保留，但不应占据一线首屏 |
| 修正合同 | 口径、权限、动作码、URL 状态、Manifest 和明细查询 | 直接修复任务无法完成或结果错误 |
| 不复活 | 四个无路由旧页面 | 它们包含已被替代的手填 ID/人工发布流程 |
| 暂不引入 | Redux、微前端、通用图表设计器、复杂缓存层、全新 UI 框架 | 不解决当前最短业务链断点 |
| 后续独立规划 | AD/OIDC、HTTPS/证书、密码策略、服务账号 ACL、安全灰度扩围 | 遵循本轮“功能优先”的明确边界 |

## 7. 本轮核心需求冻结

### 必须完成

1. 统一 CP/管理良率口径并覆盖 UNKNOWN/ABORT 回归；
2. 修复 PowerShell 5.1/7 中文路径状态闭环；
3. 修复角色默认首页、父路由、查看分析权限和 Job 重新处理动作；
4. 正式提交后自动打开新 Job，筛选/分页/Tab/分析选择可刷新恢复；
5. 历史正式数据以业务字段为主，支持多选后进入有边界的正式数据详情与比较；
6. 支持按 Dataset/Lot/Wafer/Bin/参数的服务端重算和分页明细，不再要求手填内部 ID；
7. 同 Spec 多 Lot CP 允许入库，不同 Spec 继续失败关闭；
8. Product 缺失提示与补录进入当前主流程，并影响后续查询；
9. Quick PAT 增加 Manifest 预览、下载失败反馈和服务端分页；
10. 管理首屏改为核心 KPI + 趋势 + 异常下钻，方法和维度渐进披露；
11. 完成目标测试、全量回归、真实 SQL 对账、本机浏览器 UAT 和开发库功能灰度；
12. 输出计划、完成报告、回归测试报告和可复现入口。

### 明确延期，不伪装完成

- 不同 Spec 的自动拆分和逐 Lot Spec Binding；
- 未取得真实样本和批准 Cleaner 的新厂家 Route A；
- PAT/Cpk/SPC 等尚未完成业务口径批准的正式分析；
- 任意维度拖拽式通用 BI/图表设计器；
- 生产服务器部署、生产 G3/G4 和业务签字；
- 本轮之外的安全体系建设。

## 8. 判定标准

完成后，一线用户应无需查询数据库或手填内部 ID，即可完成“提交—恢复—结果—分析—明细—导出”；领导用户应在首屏判断良率、UNKNOWN、异常和新鲜度，并能下钻到 Dataset/Job。任何当前未验证的厂家、Spec 组合或生产环境，不得在报告中写成已完成。
