## 2. 产品定位

TMS 是面向 CP/FT 测试数据的清洗调用、结构化保存、历史查询和分析平台。

系统不替代现有 Python Cleaner。现有 CP、FT Python 程序继续负责厂商文件解析和清洗业务，TMS 负责：

1. 接收用户上传；
2. 调用正确的 Python Cleaner；
3. 读取 Cleaner 输出；
4. 将清洗数据结构化保存；
5. 提供补录、查询、图表和重新导出；
6. 管理用户的数据可见范围；
7. 支持后续新增晶圆厂和封测厂 Cleaner。

## 3. 已冻结的核心原则

### 3.1 Python Cleaner 是清洗权威

- CP Cleaner 与 FT Cleaner 保持独立；
- 厂商 Parser、字段识别、单位转换、参数拆解、Bin 处理和现有统计逻辑继续由原 Python 程序负责；
- TMS 不重复实现相同厂商的清洗算法；
- 新晶圆厂、新封测厂和新格式优先在原 Python 工具中增加 Cleaner；
- TMS 读取 Cleaner 已生成的标准输出，不猜测未知字段和数值。

### 3.2 清洗数据以数据库结构化数据为长期使用主体

- Cleaner 首次运行产生的 Excel 文件只作为本次入库的临时中间产物；
- TMS 读取临时文件后，将有效内容保存为数据库结构化数据；
- 临时文件完成入库和校验后可以清理；
- 后续查询、筛选和图表主要读取数据库结构化数据；
- 用户需要 Excel 时，再次调用 Cleaner 临时生成。

### 3.3 清洗成功后直接成为正式数据

- Cleaner 成功且基础结构、数量校验通过后，数据直接成为正式可查询数据；
- 首版不增加人工审核和发布确认步骤；
- 缺少允许补录的业务字段不阻止正式入库；
- 缺失字段保持空值，不自动生成推断值。

### 3.4 用户数据按上传人隔离

- 普通用户只能查看、分析、导出、修改和删除自己上传的数据；
- 不同用户上传相同 Lot 合法且相互独立；
- 系统不得因为 Lot_ID、文件内容或 SHA 相同而自动覆盖、合并或拒绝另一用户的数据；
- 管理员拥有所有用户数据的查看、导出、重新清洗、补录修改和删除权限。

### 3.5 首版优先保证核心功能

- 普通用户删除自己的数据时允许直接从 TMS 删除；
- FTP 上的原始文件继续由既有 FTP 保存机制保留；
- 首版不要求为作废或删除建立复杂审批和长期审计；
- 补录修改记录属于核心业务记录，仍需保存。

## 4. 业务角色与权限

### 4.1 普通用户

普通用户可以：

- 上传 CP/FT 原始文件；
- 查看自己的上传任务和清洗状态；
- 查看自己的结构化清洗数据；
- 补录或修改自己的任务级业务字段；
- 对自己的数据进行查询、筛选和绘图；
- 使用最新版 Cleaner 临时生成并下载三个 Excel；
- 明确发起重新清洗并更新数据库；
- 删除自己上传的 TMS 数据。

普通用户不可以：

- 查看其他用户的数据；
- 下载其他用户的原始文件或清洗结果；
- 修改、重新清洗或删除其他用户的数据；
- 管理 Cleaner 或系统账号。

### 4.2 管理员

管理员可以：

- 管理用户和系统配置；
- 查看所有用户上传任务；
- 查看所有用户的结构化测量数据；
- 查看和下载所有用户相关文件；
- 修改全部任务的补录信息；
- 为任意任务重新执行 Cleaner；
- 删除任意用户的数据；
- 查看 Cleaner 运行状态和错误信息；
- 管理系统可用的 Cleaner。

## 5. 核心业务对象

### 5.1 上传任务

上传任务表示用户的一次上传操作，是系统管理和权限隔离的基本单位。

一个上传任务至少具有：

- 所属用户；
- CP/FT；
- 工程数据/量产数据；
- 用户选择或系统确认的厂家/Cleaner；
- 一个或多个原始文件；
- 上传时间；
- 清洗状态；
- Cleaner 运行信息；
- 补录信息；
- 清洗后的结构化数据。

上传任务编号不是业务 Lot_ID。

### 5.2 业务 Lot

- 一个上传任务可以包含一个或多个 Lot；
- 多个 Lot 通过每条记录中的 `Lot_ID` 区分；
- `Lot_ID` 在不同用户之间不唯一；
- 同一用户也可以在不同上传任务中重复上传同一个 Lot；
- 系统不得仅以 `Lot_ID` 判断数据是否重复。

### 5.3 Cleaner 运行

Cleaner 运行表示系统对一个上传任务调用一次 Python Cleaner。

业务上需要知道：

- 使用哪个 Cleaner；
- 使用哪个 Cleaner 版本；
- 运行是否成功；
- 运行时间；
- 输入文件；
- 生成了哪些结果；
- 失败时的可读错误信息。

### 5.4 结构化清洗数据

结构化清洗数据包括 Cleaner 输出文件中实际存在的业务信息。

CP 数据包括但不限于：

- Lot_ID；
- Wafer_ID；
- Die/测试序号；
- Bin；
- X/Y 坐标；
- 参数名称；
- 参数单位；
- 测试条件；
- 参数测量值；
- Spec 上下限；
- Cleaner 提供的 Yield、统计和其他源字段。

FT 数据包括但不限于：

- Product；
- Lot_ID（源数据存在时）；
- Unit/测试序号；
- 参数名称；
- 参数单位；
- 测试条件；
- 参数测量值；
- PASS/FAIL、Bin、机台和程序（源数据存在时）；
- Cleaner 提供的统计和其他源字段。

任何源文件或 Cleaner 没有提供的信息均允许保持空值。

### 5.5 任务级补录信息

补录信息默认作用于当前上传任务的全部数据。

可能补录的字段包括：

- Product；
- Lot_ID；
- 项目；
- 客户；
- 厂家/业务来源补充信息；
- 备注；
- 后续确认需要的其他任务级业务标签。

补录信息不得修改 Cleaner 原始解析值；系统需要区分 Cleaner 提供值与人工补录值。

## 6. 主业务流程

### 6.1 新建上传任务

1. 用户选择 CP 或 FT；
2. 用户选择工程数据或量产数据；
3. 用户选择厂家/Cleaner；
4. 用户上传一个或多个文件或压缩包；
5. 系统显示待处理文件；
6. 用户提交任务。

### 6.2 调用 Cleaner

1. 系统记录本次调用使用的 Cleaner 和版本；
2. 系统调用对应 Python Cleaner；
3. Cleaner 生成当前已有的标准输出；
4. Cleaner 失败时，任务显示失败原因，不保存不完整的正式结构化数据；
5. Cleaner 成功后，系统进入结构化入库处理。

### 6.3 首次清洗的三个 Excel

当前 Cleaner 生成的以下三个 Excel 都属于有效业务输出：

1. RawData 信息文件；
2. Spec/参数信息文件；
3. 统计信息文件。

RawData 文件允许包含多个 Lot，并包含 Cleaner 实际输出的 Lot、Wafer、Bin、X、Y、参数值等字段。

首次清洗产生的三个 Excel 用于：

- 读取结构化数据；
- 校验 Cleaner 是否成功；
- 核对 RawData、Spec 和统计之间的一致性。

完成数据库入库和校验后，首版不要求长期保存这三个文件。

### 6.4 正式入库

满足以下条件后，数据直接成为正式数据：

- Cleaner 返回成功；
- 要求的输出文件存在；
- RawData 可以读取；
- 核心字段结构可识别；
- 基础数量关系没有明显矛盾；
- 数据能够归属当前用户和上传任务。

缺少 Product、Lot_ID 或其他可补录字段时，数据仍允许正式入库。

## 7. 缺失字段与人工补录

### 7.1 缺失字段提醒

Cleaner 完成后，系统检查可补充业务字段。

发现缺失时，页面弹窗显示：

- 缺失字段名称；
- 缺失字段对查询或图表能力的影响；
- 用户可以填写的值；
- “暂不填写”选项。

用户选择暂不填写时，系统保持字段为空，不填入默认值。

### 7.2 缺失字段对能力的影响

- 缺 Product：不能按 Product 查询，但不阻止 CP 分析；
- 缺 Lot_ID：不能按 Lot 查询或比较，补录后恢复；
- 缺 Wafer_ID：不能按 Wafer 分析；
- 缺 X/Y：不能生成 Wafer Map；
- 缺 Bin：不能进行 Bin 分布和按 Bin 筛选；
- 缺 Spec：可以分析参数分布，但不能进行基于该 Spec 的超限判断。

系统应说明能力限制，不应阻止其他已有字段的分析。

### 7.3 CP 缺少 Lot_ID

- CP 缺少 Lot_ID 仍允许正式入库；
- 用户可以在入库后为当前上传任务补录 Lot_ID；
- 首版任务级补录的 Lot_ID 作用于该任务全部适用数据；
- 如果一份无 Lot_ID 数据实际混合多个无法识别的 Lot，系统不能自动逐行拆分；
- 用户无法确认时可以继续保持 Lot_ID 为空。

### 7.4 补录修改记录

补录或修改至少记录：

- 上传任务；
- 字段名称；
- 修改前值；
- 修改后值；
- 操作人；
- 操作时间。

首版不要求补录审批流程。

## 8. 多 Lot、参数和 Spec

### 8.1 多 Lot 入库

- RawData 中每条记录保留自己的 Lot_ID；
- 多个 Lot 可以同时存在于同一上传任务；
- 多个 Lot 可以一起分析或分别分析；
- 不得把上传任务编号当作 Lot_ID；
- 不得把第一个 Lot_ID 覆盖到 Cleaner 已识别出的其他 Lot。

### 8.2 参数和测试条件比较

同一上传任务包含多个 Lot 时，系统比较：

- 参数名称；
- 单位；
- 测试条件；
- Spec 上下限。

### 8.3 Spec 使用规则

- 参数、单位、测试条件和 Spec 完全相同：允许共用同一份定义；
- 参数相同但 Spec 不同：按 Lot 分别保存和使用；
- 某个 Lot 缺少 Spec：保持该 Lot 的 Spec 为空，不自动使用第一个 Lot 的 Spec；
- 多 Lot 分析时，每条数据根据自己的 Lot_ID 使用对应 Spec；
- 不允许无条件使用第一个 Lot 的 Spec 代替其他 Lot。

“共用同一份定义”不得丢失各 Lot 与该 Spec 的适用关系。

## 9. 历史查询与分析

### 9.1 查询条件

普通用户可以在自己的数据范围内按以下条件查询：

- 上传任务；
- 上传时间；
- CP/FT；
- 工程/量产；
- 厂家；
- Lot_ID；
- Wafer_ID；
- Product；
- Cleaner 版本；
- 清洗状态；
- 其他已保存或补录的业务字段。

管理员可以在全部用户数据范围内查询，并增加用户筛选。

### 9.2 二次绘图

历史数据入库后，用户不需要重新上传或重新运行 Cleaner 即可：

- 选择一个或多个上传任务；
- 选择一个或多个 Lot；
- 选择一个或多个 Wafer；
- 选择 Bin；
- 选择一个或多个参数；
- 重新生成图表；
- 查看清洗后的明细数据。

图表必须基于数据库中符合当前筛选条件的真实结构化数据重新计算，不能只在前端隐藏未选数据。

### 9.3 图表能力

系统后续需要支持现有参考 HTML 中适用于当前数据的图表，包括但不限于：

- Wafer Map；
- 参数 Heatmap；
- BoxPlot；
- Histogram/分布；
- Scatter；
- Correlation；
- Bin Pareto；
- Yield；
- PAT、Cpk、SPC 等后续批准分析。

具体图表优先级在后续业务评审中单独确定。

## 10. Excel 二次导出

### 10.1 默认导出行为

用户需要 Cleaner Excel 时：

1. 系统找到当前上传任务的原始输入；
2. 默认使用当前最新版 Cleaner；
3. 临时生成 RawData、Spec/参数和统计三个 Excel；
4. 三个文件均提供给用户；
5. 本次下载不修改数据库现有结构化数据；
6. 临时文件在下载完成或超过保留时间后清理。

### 10.2 版本提示

导出页面需要明确显示：

- 原数据库数据使用的 Cleaner 版本；
- 本次导出使用的 Cleaner 版本；
- 两个版本是否一致；
- 版本不一致时，导出结果可能与数据库当前数据不同。

按钮或操作名称应明确表达：

`使用最新版 Cleaner 生成下载文件`

### 10.3 下载不更新数据库

普通下载只生成临时文件，不得：

- 静默覆盖数据库当前数据；
- 修改历史图表数据；
- 修改补录信息；
- 自动执行数据库重新入库。

## 11. 使用最新版 Cleaner 重新清洗并更新数据

用户需要更新数据库时，必须主动选择独立操作：

`使用最新版 Cleaner 重新清洗并更新数据`

该操作的业务含义是：

1. 使用当前上传任务的原始输入；
2. 调用当前最新版 Cleaner；
3. 重新生成三个 Excel；
4. 重新解析和校验结构化数据；
5. 更新当前上传任务的数据库清洗数据；
6. 保留仍适用的任务级补录信息；
7. Cleaner 失败时不得破坏当前可用数据；
8. 成功后后续查询和图表使用新数据。

首版不要求在用户界面提供复杂的新旧版本管理。技术规划需要保证更新失败时原数据仍可使用。

## 12. 删除

### 12.1 普通用户删除

- 普通用户可以删除自己上传的任务；
- 删除同时清理该任务在 TMS 中的结构化数据、统计、补录信息和临时导出；
- 不影响其他用户上传的相同 Lot；
- 不删除 FTP 服务器保存的原始文件；
- 首版不要求保留删除后的业务审计记录；
- 删除前需要明确确认，防止误操作。

### 12.2 管理员删除

- 管理员可以删除任意用户上传的数据；
- 删除范围与普通用户删除一致；
- 删除不得影响其他上传任务。

## 13. 重复上传

- 同一原始文件可以被不同用户分别上传；
- 同一 Lot 可以被不同用户分别上传；
- 同一用户也可以重复上传同一 Lot；
- 系统可以提示疑似重复，但不得自动阻止、覆盖或合并；
- 每次上传均作为独立上传任务处理；
- 权限、查询、分析和删除都以上传任务所属用户为边界。

## 14. 原始文件与 FTP 边界

- FTP 服务器继续承担原始数据长期保存；
- TMS 需要记录能够定位本次上传原始输入的信息；
- TMS 删除业务数据不等于删除 FTP 原始文件；
- 二次导出和重新清洗必须能够取得原始输入；
- 如果原始输入已经无法取得，系统应明确告知无法重新生成 Cleaner 文件，不得伪造下载结果。

## 15. 失败处理

### 15.1 首次清洗失败

- 显示 Cleaner 返回的可读失败原因；
- 不保存不完整的正式结构化数据；
- 用户可以修正输入或重新提交；
- 原始上传任务可以保留失败状态供用户再次操作。

### 15.2 二次导出失败

- 不影响数据库现有数据；
- 不影响历史查询和图表；
- 不提供不完整的三个 Excel；
- 用户可以再次执行。

### 15.3 重新清洗更新失败

- 不影响当前数据库中可用的结构化数据；
- 不把失败结果设为当前数据；
- 显示失败原因并允许再次执行。

## 16. 首版业务范围

### 16.1 首版必须具备

- 用户登录；
- 普通用户数据隔离；
- 管理员全数据权限；
- CP/FT 独立上传入口；
- 调用现有 Python Cleaner；
- Cleaner 三个 Excel 的结构化入库；
- 多 Lot 保存；
- 多 Lot 参数和 Spec 比较；
- 缺失字段提示和任务级补录；
- 清洗成功后直接正式可用；
- 历史任务查询；
- 数据库数据二次绘图；
- 使用最新版 Cleaner 临时生成三个 Excel；
- 明确重新清洗并更新数据库；
- 用户删除自己数据；
- 管理员操作全部数据。

### 16.2 首版暂不要求

- 复杂审核发布流程；
- 删除后的长期审计；
- 多级业务审批；
- 自动阻止重复上传；
- 微服务化；
- 复杂消息中间件；
- 提前建设通用未知格式自动识别；
- 用户界面中的复杂数据版本对比；
- 无业务需求支撑的过度治理功能。

## 17. 业务验收场景

### BR-01 华虹 CP 单 Lot 上传

- 用户上传华虹文件；
- 系统调用原华虹 Python Cleaner；
- 数据库保存 Lot、Wafer、Bin、X/Y、参数和测量值；
- 用户可以查询和绘图；
- 临时 Excel 入库后可清理。

### BR-02 华虹 CP 多 Lot、相同 Spec

- 一个 RawData 包含多个 Lot；
- 系统保留每行 Lot_ID；
- 参数、单位、测试条件和 Spec 相同；
- 系统允许共用定义；
- 用户可以合并分析或按 Lot 分析。

### BR-03 华虹 CP 多 Lot、不同 Spec

- 多个 Lot 参数名称相同但 Spec 不同；
- 系统分别按 Lot 保存和使用 Spec；
- 图表和超限判断不串用第一份 Spec。

### BR-04 CP 缺少 Lot_ID

- Cleaner 数据没有 Lot_ID；
- 数据仍正式入库；
- 系统提示 Lot 查询能力受限；
- 用户可以以后为任务补录 Lot_ID；
- 不补录时保持空值。

### BR-05 缺少 Product

- CP Cleaner 没有提供 Product；
- 用户可以填写或跳过；
- 跳过后数据仍可按 Lot、Wafer 和参数分析。

### BR-06 不同用户上传相同 Lot

- 用户 A 和用户 B 分别上传同一 Lot；
- 两份数据均正常入库；
- A 看不到 B 的数据；
- B 看不到 A 的数据；
- 管理员可以查看两份数据。

### BR-07 最新版 Cleaner 二次导出

- 数据库原数据由 Cleaner v1 产生；
- 当前最新版为 Cleaner v2；
- 用户点击生成下载文件；
- 系统显示 v1/v2 版本差异提示；
- 使用 v2 临时生成三个 Excel；
- 数据库仍保持 v1 数据不变。

### BR-08 明确重新清洗并更新数据

- 用户主动选择重新清洗并更新；
- 系统使用最新版 Cleaner；
- 成功后数据库使用新结构化数据；
- 失败时原数据库数据仍可查询和绘图。

### BR-09 用户删除自己的数据

- 用户删除自己的上传任务；
- TMS 中该任务的数据被清理；
- FTP 原始文件不删除；
- 其他用户上传的相同 Lot 不受影响。

### BR-10 管理员全数据权限

- 管理员可以查看任意用户的数据；
- 可以下载、重新清洗、补录和删除；
- 普通用户不能通过页面或直接地址越权访问。

## 18. 已替代的旧业务口径

| 旧口径 | v0.2 当前口径 |
|---|---|
| Cleaner 后进入待审核并人工发布 | Cleaner 成功且基础校验通过后直接成为正式数据 |
| CP Lot_ID 是正式入库硬门槛 | 缺 Lot_ID 仍可入库，用户后续补录 |
| 多 Lot 禁止取第一份 Spec，但未定义复用条件 | 先比较；相同共用，不同按 Lot 保存，缺失保持空值 |
| Cleaner 首次输出作为长期文件资产保存 | 首次输出为临时入库产物，长期主体为数据库结构化数据 |
| 下载按现有 Dataset/历史 Cleaner 版本生成 | 默认用最新版 Cleaner 临时生成三个 Excel，不更新数据库 |
| 所有业务导出必须形成长期 Export Artifact | Cleaner 二次下载文件允许临时生成并按时清理 |
| 删除采用作废、审计和保留链 | 普通用户可删除自己的 TMS 数据，首版不保留删除审计，FTP 原始文件不动 |
| 数据权限考虑 Product/Project/Owner 复合范围 | 首版普通用户仅看自己的上传数据，管理员拥有全部数据权限 |

## 19. 当前无阻塞业务问题

本轮已经确认：

- Cleaner 成功后的正式数据口径；
- 多 Lot 与 Spec 处理；
- 缺 Lot_ID 入库与补录；
- 三个 Excel 的用途和生命周期；
- 最新版 Cleaner 默认导出；
- 下载不更新数据库；
- 明确重新清洗才更新数据库；
- 普通用户数据隔离；
- 管理员全数据权限；
- 删除与 FTP 边界。

后续图表优先级、具体补录字段清单和新增厂家顺序可在对应功能启动前继续评审，不阻塞本业务基线进入技术规划。
