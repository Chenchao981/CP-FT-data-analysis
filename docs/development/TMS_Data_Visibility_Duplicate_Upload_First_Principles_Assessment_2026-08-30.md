# TMS 工程/量产可见性与重复上传：第一性原理评估

- 日期：2026-08-30
- 评估方式：先事实核对，再区分业务身份、数据身份和动作权限，最后用奥卡姆剃刀选择最小闭环
- 工作状态：本文形成时仅只读评估，尚未开始本轮代码修改

## 1. 从用户真正要完成的工作出发

一线工程师使用 TMS 的目标不是管理 SHA 或 Dataset 状态，而是：

1. 上传一批工程或量产 CP/FT 数据；
2. 确认任务是否正常完成；
3. 找到自己需要分析的正式数据；
4. 对同一份量产输入重复进行独立分析时，不破坏别人已经形成的结论；
5. 工程试验不被无关人员看到，量产结果又能在组织内协作查询。

因此功能正确性的最小不变量是：

```text
工程数据：普通用户只读自己的
量产正式数据：所有 DATASET_READ 用户可读
管理动作：Owner/Admin
重复上传：每次独立，Current 仅在同一 Dataset 内切换
```

## 2. 现有系统做得好的地方

- 四个固定入口已经准确写入 `ENGINEERING/PRODUCTION × CP/FT`，不需要再猜数据类型；
- 每次上传已经创建独立 Import Batch 和 Receipt；
- Job 幂等键包含 Batch ID，不会把不同 Batch 合并；
- CP/FT Dataset Code 都包含 Batch ID，天然适合“每次上传独立分析”；
- Source Receipt 已保存本次上传快照路径和 `is_duplicate_receipt`；
- SHA 使用流式计算，适合较大文件；
- Current Catalog、分析、分页和服务端筛选已有基础，不需要重造页面。

## 3. 与新需求冲突的事实

### 3.1 Source 被错误地当成了分析身份

现有数据库以 `source_file_id` 全局限制一个 Current Processing Run；Atomic Finalizer 发布第二个同源 Batch 时，会找到旧 Source Current Run，并把旧 Run 关联的 Dataset Version 一并置为 Superseded。

后果是：

- Batch、Receipt、Job、Dataset 看似独立；
- 但第二个人上传相同内容后，第一个人的 Dataset 会退出正常分析入口；
- 多文件批次又只取第一个 Source 作为 Run 身份，首文件相同也可能错误互相影响。

根因不是“重复上传没有放开”，而是 Current 的边界放错了位置。

### 3.2 可见性规则方向相反

现有 `TMS_CURRENT_DATA` 是不区分工程/量产的全局 Grant：

- 部分管理/质量角色可以跨 Owner 看工程 Current；
- 普通 CP/FT 用户虽然有 `DATASET_READ`，却不能看其他人的量产；
- 结果页和 Job 明细还把该 Grant 用到了非 Current、失败任务和源文件血缘；
- 质量管理查询没有使用当前 Principal 过滤。

### 3.3 “可读”与“可管理”没有分离

现有页面默认可见记录都是自己的，所以很多按钮只检查 `TASK_CREATE`。量产记录向全员开放后，非 Owner 会看到“补录”“重新处理”等必然失败的按钮。

### 3.4 前端缓存没有用户边界

React Query 使用全局缓存，退出、重新登录和认证失效没有统一取消查询与清空缓存。同一浏览器切换用户时，上一用户的工程数据可能短暂留在页面中。

### 3.5 并发重复上传存在 Source 唯一键竞态

Source 注册使用“先查 SHA、再插入”，没有 key-range lock。两名用户同时上传相同内容时可能同时查不到 Source，随后一方撞唯一键并整批失败。

## 4. 第一性原理拆分

| 身份 | 含义 | 正确唯一边界 |
|---|---|---|
| Source | 文件内容相同 | SHA-256，可复用 |
| Receipt | 某用户某次收到/上传该内容 | 每次上传独立 |
| Batch | 本次业务提交 | 每次上传独立 |
| Job/Run | 本次 Cleaner 执行 | 每次分析独立 |
| Dataset | 本次上传形成的可分析数据资产 | 每个 Batch 独立 |
| Dataset Version | 同一 Dataset 的重处理版本 | Dataset 内 Current 唯一 |

只要不混淆这六层，重复上传无需建设复杂“去重引擎”。

## 5. 奥卡姆剃刀评估

### 5.1 采用的最小方案

1. 保留 Source SHA 复用和 Receipt 独立；
2. 删除 Source 级 Current 唯一约束；
3. Finalizer 只 Supersede 同一 Dataset 的上一 Version 及其 Run；
4. 用一个域感知 SQL 规则替代 `TMS_CURRENT_DATA` 的业务查询用途；
5. 后端返回 `can_manage`/重复来源信息，前端不猜动作权限；
6. 身份切换时取消并清空前端查询缓存；
7. 用锁定 get-or-create 解决同 SHA 并发注册。

### 5.2 本轮不采用的复杂方案

- 不增加微服务或独立权限服务；
- 不按 SHA 自动复用旧分析结果；
- 不把量产共享实现成前端合并多个 Owner 查询；
- 不引入 Redis/搜索引擎解决当前规模分页；
- 不在没有真实执行计划前大规模增加索引；
- 不把本轮功能规则包装成完整安全治理项目。

## 6. 前端核心需求

- 工程页明确“仅本人数据”；
- 量产页明确“正式结果全员共享、管理动作仍属于上传人”；
- 同 Lot/同内容记录显示上传人、Batch、时间和重复来源；
- 共享量产行保留分析/Job 入口，隐藏补录和重处理；
- 登录用户变化后页面先清空旧数据，再加载新身份范围；
- 重复上传成功提示说明“已创建独立任务，不覆盖历史结果”。

## 7. 性能判断

- 范围过滤必须下推 SQL，不能查询后过滤；
- 现有 Import Batch 索引以 Domain/Stage/Owner/Time 排列，工程 Owner 查询适配较好，量产跨 Owner 时间分页需要真实执行计划再决定是否增加专用索引；
- Current Catalog、质量摘要和最多 8 Dataset 比较是重点测量路径；
- 当前开发库规模只能证明开发规模性能，不能外推生产峰值；
- 深页 OFFSET、Compare N+1 和质量 CTE 多次聚合登记为性能观察项，先用实测决定优化顺序。

## 8. 结论

本轮不需要重做 TMS。最小正确路径是把三个错误边界纠正：

1. Current 从 Source 边界移回 Dataset；
2. 读取从全局 Grant 改成工程/量产业务域规则；
3. 前端从“有功能权限就显示按钮”改成“服务端确认可管理才显示”。

完成后才能真实满足“能用、好用、重复分析互不影响”。
